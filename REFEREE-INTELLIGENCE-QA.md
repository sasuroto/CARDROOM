## 4. Автоматическое обновление

- **Точка входа:** `GET /api/referee-journal?next=1`. Вызывать каждые 10 минут из расписания Sites — инструкция добавлена в `/api/referees`.
- **Cron Worker (необязательный):** `scheduled()` в `build/sites-worker.ts` выполняет тот же шаг. Сейчас сборка генерирует `triggers:{}`, поэтому cron включается только на стороне платформы.
- **Порядок лиг:** за вызов обрабатывается не больше одной лиги. Сначала никогда не собиравшиеся, затем проверенная раньше всех. Каждая лига — не чаще раза в час.

**Ограничение частоты запросов к ESPN:**
- между запусками любых лиг — не меньше 5 минут;
- за запуск — не больше 6 запросов календаря и 30 запросов матчей, не дольше 45 секунд;
- между запросами — не меньше 400 мс (≤ 2,5 запроса в секунду);
- ответ 429 → общая пауза по `Retry-After` (минимум 1 час) для журнала, назначений и `/api/match`;
- данные матчей, уже закэшированные `/api/analysis`, используются повторно без запроса.

**Оценка нагрузки:**
- худший случай — ≤ 12 запусков и ≤ 432 запроса в час;
- после первичного сбора — около 40–60 запросов в час на все 9 лиг;
- первичный сбор займёт около 4–5 часов: лиге со ~110 матчами нужно 4 часовых прохода.

## 7. Сверка с первичными источниками — после тестового деплоя

Не выполнена: первичные источники недоступны из среды разработки.

Процедура (около 30 минут):
1. Через 5–6 часов после запуска расписания открыть `/api/referee-journal`. По каждой лиге сравнить `coverage.finished` с числом сыгранных матчей на странице турнира ESPN. Расхождение больше 0 — разобрать `errors`.
2. Выбрать 3 матча на лигу: последний тур, июль/август, матч без арбитра. Сверить арбитра, ЖК и КК с официальным протоколом или страницей матча лиги (premierleague.com, laliga.com, legaseriea.it, bundesliga.com, ligue1.com, tff.org, ligaportugal.pt, uefa.com).
3. Повторный сбор: записать `records.length` по каждой лиге, дождаться 2 следующих проходов. Число не должно уменьшиться, дубликатов быть не должно — проверяется по уникальности `id` в `?read=1`.
4. Принять решение по пенальти: либо проверенный разбор ESPN, либо платный API.

## 9. Тестовый деплой (staging)

Статус на 17.10.2026: **не развёрнут** (ожидает действий владельца из списка ниже). Из среды разработки нет учётных данных Cloudflare или Sites, а сеть блокирует `api.cloudflare.com`, `*.workers.dev` и ESPN.

Подготовлено:
- **`node scripts/deploy-staging.mjs`** — отдельный Worker `cardroom-referees-staging` и отдельный R2 `cardroom-referees-staging`.
  - Cron `*/10`, публикация только на workers.dev.
  - Скрипт отказывается работать с production-именами и маршрутами домена.
  - `--dry-run` проверен: bindings только staging, размер в gzip — 390 КБ.
- **`node scripts/staging-check.mjs <url> --cycles 5 --interval 11`** — QA в реальном времени, без имитации:
  - API и валидация;
  - циклы с настоящими паузами;
  - покрытие по лигам, дубликаты, уменьшение числа записей;
  - рендер карточек в headless Chromium;
  - выборка матчей для ручной сверки.
  - Механика проверена на локальном Worker.

### Что нужно от владельца (секреты в чат не передаются)

**A. Cloudflare — staging-деплой.** API-токен создаётся в Cloudflare: My Profile → API Tokens → Create Custom Token, область — только ваш аккаунт, без зон.

| Разрешение | Уровень | Зачем |
|---|---|---|
| Account · Workers Scripts | Edit | Загрузить Worker `cardroom-referees-staging`, cron и workers.dev |
| Account · Workers R2 Storage | Edit | Создать и использовать bucket `cardroom-referees-staging` |
| Account · Workers Tail | Read | Необязательно: логи staging при разборе ошибок |
| User · User Details | Read | Только если wrangler попросит при деплое |

Кроме токена:
- У аккаунта должен быть включён поддомен workers.dev (Workers & Pages → Overview — один раз в панели).
- В настройках облачной среды (меню среды → Edit):
  - переменные `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID` в разделе Network secrets или как переменные окружения;
